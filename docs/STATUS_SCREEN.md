# MUGEN ZERO ステータス画面 — 実装メモと将来設計

対象: `packages/mugen-app`（mugen-app が正式な開発の中心）
関連: `STATUS SYSTEM MASTER SPEC v0.1`、および頂いたイメージ画像（構図の指定）

この文書は二部構成です。

- **第1部** — 今の画面が「何を出し、何を出さないか」と、その根拠。
- **第2部** — 将来の着せ替えのための `CharacterAppearance` / `SkinDefinition`
  分離設計。**今回は実装しません。設計案の文書化のみです。**

---

## 第1部 — 今のステータス画面

### 1-1. 表示している項目と、その数値の出どころ

この画面は**数値を一つも計算しません**。すべて既存のデータを読むだけです。

| 表示 | 出どころ | 備考 |
|---|---|---|
| 名前 | `activeParty()` の `label` | パーティー名簿。画面内に名前の一覧は持たない |
| LEVEL / 99 | `world.getProgress(id).level`、`MAX_LEVEL` | 上限は `levelCurve` の定数 |
| NEXT | `expToNextLevel(progress)` | 最大レベルでは「（最大）」 |
| 経験値バー | `levelBand(progress)` の `into / span` | **バーのために画面側で計算し直さない**ための関数 |
| HP | `world.getPartyCondition()[id]` の `currentHp / maxHp` | 戦闘が使う残量と同じ |
| MP | 同上 `currentMp / maxMp` | |
| 攻撃力 | `world.getPartyStats()` の `attackMin〜attackMax` | 戦闘が戦闘キャラを組み立てるのと同じ関数 |
| 武器種 | `BATTLE_PROFILES[id].weaponType` → `weaponLabelOf()` | CANON。主人公＝長剣 |
| 戦闘スタイル | `BATTLE_PROFILES[id].battleStyle` | ケイオス＝魔法特化 |

同じ数値を二箇所で計算しないことが前提です。もしこの画面と戦闘が最大 HP で
食い違ったら、**正しいのは戦闘のほう**で、この画面のほうが存在してはいけない
二つ目の計算だ、ということになります。

### 1-2. 表示していない項目と、その理由

MASTER SPEC v0.1 には 防御力・魔力・装備名 が挙がっていましたが、確認のうえ
**「存在するものだけ出す」**という方針を頂いたため、次の項目は行ごと存在しません。

| 出していないもの | 理由 |
|---|---|
| 防御力 | `PartyStats` に防御値が無い。戦闘計算にも防御ステータスは存在しない（設計上の決定） |
| 魔力 | 同上。魔法の強さは魔法側の定義であって、キャラの能力値ではない |
| 素早さ | 同上。行動順のステータスは存在しない |
| 装備武器名 | 装備システムそのものが無い。武器「種」は CANON だが、装備品データは無い |

**「0」「—」「未実装」といった仮表示も置いていません。** 仮の数値は誰も決めて
いない数値であり、それを出すことは画面がプレイヤーに嘘をつくことになるためです。
`status.tsx` の行リストは配列なので、これらが実在する日には行を足すだけで済みます。

### 1-3. 誰が表示されるか

`activeParty()` が返した人だけです。画面内に人名を書いた配列はありません。

- **主人公・ケイオス** — 現在のパーティー。2人だから2人出ているだけで、
  2人に固定してはいません。仲間が増えた日、この画面は**触らずに**増えます。
- **レヴィ（SPEAR）・アリア（BOW）** — 武器種 CANON は `WEAPON_CANON` に
  ありますが、キャラクター本体（`BATTLE_PROFILES` の項目）は作っていません。
  未加入のキャラクターを仮データで生成しないためです。
- **ガルド（DUAL_DAGGER）** — 同上。四択や更生ルートで戦闘パーティーへ
  自動加入させる処理は入れていません。敵 NPC のままです。

### 1-4. イメージ画像との対応

頂いたイメージ画像は**構図の指定**として受け取り、次のように反映しました。

**採用した構図**

- 立ち絵を**右**に、全身が切れない高さで配置（`object-fit: contain`。
  横長の画面で顔や身体が不自然に切れないようにするため、`cover` は使いません）
- 画面上部にキャラクター切替タブ（主人公 / ケイオス）
- 左側に 名前 → LEVEL（数字を大きく、上限と NEXT を小さく添える）→ 経験値バー
  → HP / MP / 攻撃力 → 武器種・戦闘スタイル の順で読み下す配置
- 武器種と戦闘スタイルを、能力値の行ではなく**独立した2つの枠**として扱う

**今回採用しなかった要素と、その理由**

| 画像内の要素 | 採用しなかった理由 | 出せる条件 |
|---|---|---|
| LEVEL 80 / 100、HP 4,320 (+980) 等の数値 | 画像上の例示値。実データは LEVEL 1 から始まる。数値は捏造しない | —（実データを表示中） |
| 防御力 / 魔力 / 素早さ | 1-2 のとおりステータスが存在しない | 戦闘計算にそのステータスを足す設計が決まった時 |
| 武器種「魔導書（グリモワール）」 | ケイオスの武器種は**未確定**という決定。杖や魔導書を勝手に正式装備として追加しない、というご指示による。現在は武器種の代わりに「魔法」と表示 | ケイオスの物理武器種を決めた時 |
| 戦闘スタイル「魔法 / 支援」 | 支援スタイルの定義が無い。現在は「魔法特化」 | `BattleStyle` に支援系を足す設計が決まった時 |
| 左のメニュー（スキル / 装備 / ストーリー / ボイス） | どれも未実装。押せない項目を4つ並べるのは仮表示にあたる | 各機能が実装された時 |
| 下部の「プロフィール / 装備 / スキン」ボタン | 同上。特にスキンは第2部のとおり設計のみ | 同上 |
| キャラクター台詞・紹介文・縦書きのコピー | テキストデータが無い。物語の台詞を勝手に作らない | 台詞データを頂いた時 |
| 顔アップの差分立ち絵 | `statusPortrait` とは別の差分。第2部の `assetRefs` で受け皿だけ用意 | 差分画像と、表示する差分の指定を頂いた時 |
| 装飾（枠・背景・箔・グラデーション） | App Alpha は意図的に素の見た目。**構図だけ**を先に合わせ、装飾は素材と一緒に入れる段階 | 背景・枠素材を頂いた時 |

つまり今回入れたのは **「正式なステータス画面という土台」と、その土台を
イメージ画像の構図に合わせること**までです。

### 1-5. 立ち絵の読み込み

`packages/mugen-app/src/assets/portraits.ts`。`areas.ts` と同じ規則で、
**マニフェストではなく1ファイルずつの動的 import** です。マニフェストを
名指しするとゲームの全アセットが一つのチャンクに入るためで、実際に以前
エリア読み込みの初版で、一音も鳴らしていないアプリがフルサイズの MP3 を
6本取りに行ったことがあります。

キーは `portraitKey`（キャラ ID でも名前でもない）です。これが第2部の
スキンが入ってくる継ぎ目になります。

## 第2部 — 将来設計: CharacterAppearance と SkinDefinition

**今回は実装しません。** 着せ替えの実装・購入処理・SAVE schema 変更は
行わず、互換性を含む将来の設計案としてのみ記録します。

### 2-1. なぜ2つに分けるのか

「そのキャラが今どう見えているか」と「その見た目そのものの定義」は、
寿命が違います。

- **選択（誰が何を着ているか）** — SAVE に入る。プレイヤーの持ち物。
- **定義（その衣装が何なのか）** — ビルドに入る。差し替え・追加・修正される。

これを一つの構造にすると、衣装を1着追加するたびに SAVE の形が変わります。
分けておけば、SAVE には**文字列 ID が1つ**入るだけで済みます。

### 2-2. 型（案）

```ts
/** SAVE に入りうる側。キャラごとに1つ。 */
interface CharacterAppearance {
  characterId: string;
  /** そのキャラの既定スキン。ビルド側の真実で、SAVE には書かない。 */
  defaultSkinId: string;
  /** プレイヤーが選んだもの。未選択なら null（＝既定を使う）。 */
  selectedSkinId: string | null;
}

/** ビルドに入る側。SAVE には絶対に入らない。 */
interface SkinDefinition {
  skinId: string;
  characterId: string;
  displayName: string;
  assetRefs: SkinAssetRefs;
  availability: SkinAvailability;
  /** 素材を差し替えた時に上げる。キャッシュ更新の判断に使う。 */
  version: number;
}

interface SkinAssetRefs {
  statusPortrait: string;
  normal: string;
  angry: string;
  sad: string;
  battle: string;
  skill: string;
  cutIn: string;
}
```

`availability` は「持っているか」ではなく「配布上どういうものか」を表します
（既定 / 配布済み / 期間限定 / 未公開 など）。**購入処理・所持判定は今回の
設計対象外**で、所持リストを SAVE に足す形になるはずですが、それは着せ替えを
実装すると決めた時に別途設計します。

### 2-3. スキンが変えないもの（重要）

スキンは**見た目だけ**です。次は一切変わりません。

- キャラクター ID
- 能力値（HP / MP / 攻撃力、レベル、経験値）
- 武器種（`WEAPON_CANON`）と戦闘スタイル
- 装備
- WORLD MEMORY に記録される出来事
- 物語・台詞・分岐

したがって `SkinDefinition` に能力値やステータス補正のフィールドは
**意図的にありません**。ここに1つでも数値を足した瞬間、着せ替えは
「強い衣装」になり、ゲームの性質が変わります。

### 2-4. 解決の流れ

```
characterId
  → CharacterAppearance（selectedSkinId ?? defaultSkinId）
  → SkinDefinition
  → assetRefs.statusPortrait
  → portraits.ts が1ファイルだけ取りに行く
```

今日の `portraits.ts` は `portraitKey` を受け取って1枚返します。将来は
この `portraitKey` を「誰か」からではなく「その人の appearance」から
決めるようになるだけで、**ローダー側の形は変わりません**。これが今回
キーをキャラ ID にせず `portraitKey` にした理由です。

### 2-5. 互換性

| 場面 | 起きること |
|---|---|
| 今の SAVE（appearance の項目が無い）を読む | 項目が無い＝未選択。`defaultSkinId` が使われ、今と同じ見た目になる |
| 選択中のスキンがビルドから消えた | `SkinDefinition` が引けない → 既定へ戻す（画面を失わない）。選択は SAVE に残したまま、復活すれば戻る |
| 素材を差し替えた | `version` を上げる。ID は変えない。SAVE は無傷 |
| スキンを追加した | ビルド側だけの変更。SAVE schema は変わらない |
| キャラが増えた | そのキャラの `defaultSkinId` が増えるだけ |

**SAVE schema の変更は今回行いません。**「将来のスキン拡張のために
SAVE schema を変更すること」も禁止というご指示を受けており、実際に
変更していません。上の表は、実装すると決めた日に schema をどう足せば
既存 SAVE が壊れないか、という見取り図です。

### 2-6. 実装すると決めた時の順序（案）

1. `SkinDefinition` の登録簿をビルド側に作る（既定スキンのみ、1キャラ1件）
2. `portraits.ts` の解決を appearance 経由に差し替える（見た目は変わらない）
3. その状態で回帰テスト。**ここまでで SAVE は一切変わらない**
4. ここで初めて SAVE への `selectedSkinId` 追加を設計・確認
5. 所持と購入は、さらにその後に別途
### 1-6. 表情集（2枚目のイメージ画像より）

2枚目のイメージ画像に「EXPRESSIONS｜表情集 — 通常 / 微笑 / 憤り / 悲しみ」が
示されました。これは MASTER SPEC の `assetRefs` と概ね一致しますが、**一点
だけ足りません**。

| 画像の表情 | SPEC の `assetRefs` |
|---|---|
| 通常 | `normal` |
| 微笑 | **対応するキーが無い** |
| 憤り | `angry` |
| 悲しみ | `sad` |

`SkinDefinition.assetRefs` は SPEC で
statusPortrait / normal / angry / sad / battle / skill / cutIn と指定されて
いますが、画像には「微笑」があります。`smile` を足すかどうかは**作者の決定
事項**として保留し、勝手に追加していません（第2部 2-2 の型は SPEC のまま）。

また画像には**全身の立ち絵**と**顔のアップ**が別々に置かれています。
`statusPortrait` がどちらを指すのかも未確定なので、現在の実装は
「`portraitKey` で1枚引く」ところまでです。

## 第3部 — デザイン実装指示書を受領（本実装は保留）

「ダサくない、世界観に溶け込む、高級感のあるステータス画面」の実装指示書を
受領しました。**まず「ラフUI案を2案」を提出し、比較のうえ本実装へ進む**という
進め方の指示があるため、**この文書の時点では本デザインは未実装です。**

現在の実装（第1部）は App Alpha の素の見た目のままで、土台としての
データ経路・切替構造・立ち絵ローダーが完成している状態です。
デザイン実装はこの土台の上に載せ替える形になります。

### 指示書のうち、データを待つ項目

| 項目 | 状態 |
|---|---|
| 戦闘スタイル説明文 | **受領済み**（指示書 §8 に主人公・ケイオス両方の固定文） |
| ケイオスの肩書き | 指示書 §7 に「記憶を導く双翼の少女」の記載あり。**正式採用かは要確認** |
| 主人公の肩書き | **未提供** |
| 人物紹介文（両名） | **未提供**。§8 の戦闘スタイル文とは別枠のため、捏造しない |

### 指示書とイメージ画像の食い違い

指示書 §5・§15 は「**左**に立ち絵／右に情報」ですが、頂いた2枚のイメージ画像は
いずれも立ち絵が**右**です。ラフUI案は指示書の文面に従い両案とも立ち絵を左に
置いています。左右反転が必要な場合は指示をください。

### 配色について

指示書 §9 はアイボリー基調の**明るい配色**ですが、現在のアプリ全体は
暗色テーマ（`--bg: #0b0b12`）です。ステータス画面だけを明色にすると
他画面との落差が大きくなるため、次のいずれかを選ぶ必要があります。

1. ステータス画面のみ明色（指示書どおり。画面遷移で明暗が切り替わる）
2. アプリ全体を明色基調へ寄せる（影響範囲が大きい、別ラウンド相当）

ラフUI案は 1 の前提で描いています。

### フォントについて

理想は明朝系ですが、**現在のビルドには日本語の明朝フォントが含まれていません**
（検証環境で利用可能な日本語フォントは IPAGothic のみ）。ラフUI案の
スクリーンショットもゴシックで描画されています。明朝にするには
Noto Serif JP 等の同梱が必要で、これは**外部素材の取得にあたるため、
指示を受けるまで取得しません**。
